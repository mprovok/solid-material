# Port Storybook play functions to interaction tests

## Summary

Move the 13 play functions currently living in 9 story files into the repo's `*.test.tsx` interaction tests (Vitest Browser Mode + Playwright, `components` project, developed against **Chromium**). Two layout stories have no sibling interaction test at all, so their plays (the only behavioral coverage those layouts have) are ported into two new test files; the seven component stories already have sibling `*.test.tsx` files, so their plays are ported as additive `it` blocks, skipping the parts those files already cover. After the ports are green, the `play` functions (and the now-unused `storybook/test` imports) are removed from the stories — the coverage moves from the `storybook` project to the `components` project. No production code is touched; no VRT files or baselines are involved.

## Current state

- **Plays run only in the storybook project**: `packages/material/vitest.config.ts` defines three projects; plays in `*.stories.tsx` execute under the `storybook` project using `storybook/test` (`canvas`, `step`, `fn`, `waitFor`, `within`, `userEvent`). Interaction tests live in the `components` project (`src/**/*.test.{ts,tsx}`), use `render` from `@solidjs/testing-library`, `page`/`userEvent` from `vitest/browser`, `expect.element(...)`, `vi.fn()`, `vi.waitFor`, and Given/When/Then comment blocks — see `components/radio/MaterialRadio.test.tsx` or `components/carousel/MaterialCarousel.test.tsx` for the style.

- **What the sibling files already cover** (dedupe targets, verified by reading them):

  - `MaterialMenu.test.tsx`: only `Accessibility` tests (open static menu, one submenu). **Not covered**: any keyboard navigation — the whole `Submenus` play is new.
  - `MaterialNavigationRail.test.tsx`: arrow/Home/End focus cycling (`can move focus to its items using keyboard`), appearance-while-hidden, secondary items, a11y. **Not covered**: `aria-current` navigation (Enter/click).
  - `MaterialRadio.test.tsx`: single-radio onChange, guards, disabled, props, a11y. **Not covered**: the controlled group behavior of the `WithLabel` play.
  - `MaterialSnackbarContainer.test.tsx`: close via close button, close via action, next snack after exit — all seeded **directly into a test-local store** via `MaterialSnackbarContext.Provider`. **Not covered**: the `showSnack`-driven end-to-end flow of the play (which uses the module-level default store).
  - `MaterialSplitButton.test.tsx` (describe `MaterialSplitButtonMenu`): label-button `onClick`, switch `onToggle`, a11y with the menu open (opens via switch click). **Not covered**: focus placement on open + Enter activation of a menu item.
  - `MaterialFabMenu.test.tsx` targets `MaterialFabMenu` — a **different component** from `MaterialFabWebMenu` (`MaterialFabWebMenu.tsx` renders `MaterialFab` + `MaterialMenu` with a `menuAriaLabel`), so its play gets a new sibling file, matching the one-file-per-component convention.
- **Layouts have no interaction tests**: `layouts/canonical-layouts/list-detail-layout/` and `layouts/navigation-layout/` only have `*.vrt.test.tsx` files. The list-detail VRT already performs the same interactions for screenshots (with a `SETTLE_TRANSITIONS_MS` settle and `toMatchScreenshot`), and its fixtures are reusable: `ListPane`, `Wrapper`, `renderComponent` with `page.viewport(...)` set **before** render, viewport constants `COMPACT_VIEWPORT` (375×667) / `EXPANDED_VIEWPORT` (1024×768) — never exceed 1280×720 (viewport persists across tests within a file). The navigation-layout VRT provides the router `Wrapper` (`MaterialTheme` + `<Route path="*">`) and the items fixture with the `end: true` root item.
- **API mapping** plays → interaction tests: `canvas.getByRole/findByRole` → `screen.getByRole(...)` + `await expect.element(...)`; `within(separator).getByRole(...)` → `separator.getByRole(...)` on the locator; `fn()` → `vi.fn()`; `waitFor` → `vi.waitFor`; `step` → separate `it`s or Given/When/Then comment blocks; `userEvent` from `vitest/browser`; `toHaveFocus`/`toHaveAttribute` available on `expect.element`. `storybook/test` imports are never allowed in `*.test.tsx`.
- **Web-component query caveat** (established in `MaterialMenu.test.tsx` / `MaterialSplitButton.test.tsx` headers): `md-menu`/`md-menu-item` set their roles via element internals, so role queries cannot resolve them — locate hosts via `getByElement('md-menu[aria-label]')` and items via `getByText(...)`, and assert focus via `toHaveFocus` on those locators. The same applies to `MaterialFabWebMenu`'s `md-menu`.
- **Radio `checked` caveat** (`MaterialRadio.test.tsx` header): `md-radio`'s `checked` **property** does not reflect to an attribute after an uncontrolled click. In the `WithLabel` story, however, the parent drives `bool:checked` from a signal, so the attribute flips when the group state changes — the ported fixture must keep that controlled shape for the play's attribute assertions to work.
- **Snackbar store caveat** (`MaterialSnackbarContainer.test.tsx` harness comment): the module-level default store leaks state between tests; the existing tests avoid it with a local `Provider`. `showSnack` resolves the **default** store when called from a click handler outside a Provider (proven by `MaterialSnackbarContext.test.tsx`, which also shows the `afterEach` reset pattern via `MaterialSnackbarContext.defaultValue`).
- Plays used `delay: 250` keystrokes and 800 ms+ settles because pane/menu animations are transition-gated; interaction tests should assert with `vi.waitFor`/`expect.element(...)` polling instead of fixed sleeps.

## Risks and open questions

- **Focus placement on menu open is asynchronous** (`md-menu` focuses its first item after the open transition): the plays relied on the click `delay` to paper over this. Use `vi.waitFor` around the first `toHaveFocus` assertion in Steps 4, 8 and 9; if focus never lands in headless Chromium, that is a finding to report, not a test to weaken.
- **Pane/menu state flips may be transition-gated**: the list-detail plays used 250 ms keystroke delays and 800 ms settles. Prefer `vi.waitFor`/`expect.element` polling over fixed sleeps; only add a short settle if a transition genuinely defers the DOM change.
- **`aria-current` and `data-expanded` assertions after Enter/click on the rail** (Steps 2 and 5) may lag the navigation's animated state — poll with `vi.waitFor`.
- **`userEvent.tab()` sequencing** (Step 3): tab order starts from the currently focused element; each test must render fresh (the automatic `cleanup()` guarantees this) so Tab begins at `document.body`. The stories' trailing `button.blur()` calls are storybook-hygiene only and are not needed.
- **Radio attribute assertion only holds in the controlled fixture** (Step 6): `bool:checked` from a signal flips the attribute, but an uncontrolled click does not (see the existing file's comment). If the attribute does not update even in the controlled fixture, fall back to the `checked` property via `expect.poll` and keep the label-text assertions as the behavioral core.
- **Default-store snackbar test** (Step 7): `showSnack` from a click handler resolves the module-level default store (proven by `MaterialSnackbarContext.test.tsx`); if the popover positioning misbehaves without the story CSS anchors, reuse the exact story markup from the play rather than inventing wrapper styles.
- **Chromium is the only browser**: tests are developed and verified on Chromium, matching the repo's default browser instance and prior plan.
