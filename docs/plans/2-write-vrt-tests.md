# Visual regression tests for card, checkbox, chips, dialog, divider, menu, progress, radio, select, slider, snackbar, switch, tabs, and text field

## Summary

Add visual regression tests (VRT, `*.vrt.test.tsx` files using `toMatchScreenshot()`) for the fourteen components that currently have no screenshot coverage: `MaterialCard`/`MaterialCardBody`, `MaterialCheckbox`, `MaterialChip`/`MaterialChipSet`, `MaterialDialog`, `MaterialDivider`, `MaterialMenu`/`MaterialMenuAnchor`/`MaterialMenuItem`/`MaterialSubMenu`, `MaterialProgress`, `MaterialRadio`, `MaterialSelect`, `MaterialSlider`, `MaterialSnackbarContainer`, `MaterialSwitch`, `MaterialTabs`/`MaterialTab`, and `MaterialTextField`/`MaterialPasswordField`. The component implementations are already reviewed with no major findings, so the baselines capture the current reviewed visual state as-is — no production code changes are expected or in scope; the finished test implementation itself must also pass a review with no major findings. Tests are developed, run, and baselined against **Chromium** on Linux (`-chromium-linux.png` baselines, following the `MaterialButtonGroup`/`MaterialSideSheet`/previous-batch precedent); WebKit (`-webkit-darwin`) baselines are explicitly out of scope and will be added later in CI — this gap is accepted and must not be "fixed" by committing Linux-generated WebKit baselines. Interactive-state captures (open menus/dialogs, hovered or focused sliders) appear only in the dialog, menu, and slider files; the other eleven files are static-only. The indeterminate progress states are **not** tested because they are timing dependent (and `fourColor` is skipped with them, since it only pairs with indeterminate in the stories). Nothing is committed by the implementing agent — all new files are left in the working tree for the requester to commit.

## Risks and open questions

- **Slider value-label bubble** — whether `md-slider` reveals the value label on hover (vs. only on pointer-down or not at all without interaction) is unverified here; the static `labeled` captures may or may not include the bubble. The interactive hover/focus captures are the ones that may need tuning: if the bubble only appears while the pointer is down, port the `pressAndHold` race from `MaterialButtonGroup.vrt.test.tsx`; if it never appears on hover, keep the handle hover-state capture or drop the bubble capture — the static matrix remains the deliverable.
- **Submenu hover-open flakiness** — `md-sub-menu` opens on pointer enter; the hovered item shows its own hover state layer in the screenshot (deterministic as long as the pointer stays parked during the settle wait). If hover-open proves unreliable, use the keyboard route from the `Submenus` story play function (`ArrowDown`×2 + `ArrowRight`, focus-based states are equally deterministic).
- **Menu placement overflow** — the eight placements are captured against a flex-centered anchor in an ~800×600 wrapper; if any placement pushes the menu outside the screenshot box (or the viewport), drop that placement and note the gap rather than shrinking the wrapper mid-run (all captures must share the fixture).
- **Dialog scrim coverage** — the `md-dialog` host is expected to cover the viewport (scrim + surface inside its box); if the host hugs only the surface, switch those screenshots to the page-area locator (app-bar precedent) so the scrim is captured. The open-transition settle wait mirrors the side-sheet dialog precedent either way.
- **Snackbar fixture is a test-only construct** — a fresh `MaterialSnackbarContext.Provider` with a local store (instead of the module-default store + `showSnack`) is required for test isolation; it exercises the same code path (`setState` append + container `state.at(-1)`). The popover positioning depends on the anchor names declared in the imported stories CSS; Chromium supports the popover API and CSS anchor positioning (baseline-2025 targets), so no fallback is expected. If the enter transition does not settle within 800 ms, lengthen `SETTLE_TRANSITIONS_MS` for this file.
- **Checkbox indeterminate matcher** — `toBePartiallyChecked()` requires `aria-checked="mixed"` to resolve through the shadow DOM; if it does not, assert the indeterminate visual only (the state is still captured by the screenshot). `required`/`inert` (checkbox, radio, switch) have no visual difference and are intentionally not captured.
- **Width-sensitive components** — select and text field fixtures need fixed-width wrappers (they stretch to the container); sliders and tabs likewise. Without them the element screenshots depend on the body width and would be brittle.
- **File size** — the chip and text-field matrices are the largest; if either file approaches the `max-lines` 1000 limit, keep fixtures shared at the top of the file and prefer `it.each` over copy-pasted tests rather than splitting into a second file.
- **WebKit baselines** — until CI generates `-webkit-darwin` baselines on macOS, the visual project fails on WebKit for these fourteen files; this is explicitly accepted for this task and must not be "fixed" by committing Linux-generated WebKit baselines.
- **Number text-field spinner** — Chromium may render native spinner affordances on `type="number"` fields; whatever it renders is captured deterministically for the Chromium baselines, and the `noSpinner` variant is captured alongside it. Any WebKit rendering difference is a CI baseline concern, not a test change.
