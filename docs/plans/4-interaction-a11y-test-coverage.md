# Interaction and a11y tests for 13 under-tested components

## Summary

Add 13 new browser interaction/a11y test files (`*.test.tsx`, Vitest Browser Mode + Playwright, developed against **Chromium**) to close measured istanbul coverage gaps in the `components` project of `packages/material`. Every file is new — no existing test file is modified, no VRT (`*.vrt.test.tsx`) files or screenshot baselines are involved. The gaps are behavioral (pointer drag, keyboard navigation, event guards, close/timer wiring, context defaults, prop-binding branches) that interaction tests are the right tool for; production code is not touched. The measured baselines below come from an istanbul full-package run; the deliverable is that every listed uncovered region is exercised except the ones each component's "out of scope" note declares unreachable or low-value.

## Current state

- **Test infrastructure**: `packages/material/vitest.config.ts` defines three projects; the `components` project includes `src/**/*.test.{ts,tsx}` (excluding the VRT pattern), uses `vitest.setup.ts` (custom `getByElement(tag)` locator, automatic testing-library `cleanup()` after each test), browser instance `chromium`, default viewport 1024×768, istanbul coverage with `reportOnFailure: true`. Running `--browser chromium` filters to the Chromium instance (the requested development browser).
- **Established interaction-test patterns** (to reuse, all under `packages/material/src/components/` unless noted):
  - `render(() => <Component … />, { wrapper: MaterialTheme })` → `const screen = page.elementLocator(baseElement)`; `await document.fonts.ready`; Given/When/Then comment blocks; spies via `vi.fn()` and `toHaveBeenCalled*` matchers (incl. `toHaveBeenCalledExactlyOnceWith` in `checkbox/MaterialCheckbox.test.tsx`).
  - Focusing elements directly (`items.nth(0).element().focus()`) then `userEvent.keyboard('{ArrowRight}')` / `toHaveFocus` (`navigation-bar/MaterialNavigationBar.test.tsx`).
  - Router-dependent components (anything rendering `<A>` from `@solidjs/router`, i.e. navigation items): `MaterialTheme` + `<Route path="*">` wrapper plus the `location: '/'` render option (`navigation-rail/MaterialNavigationRail.vrt.test.tsx`).
  - Viewport-sensitive rendering: `await page.viewport(w, h)` **before** `render` — the viewport persists across tests within a file, so every render helper sets it explicitly; never exceed 1280×720 (`layouts/canonical-layouts/supporting-pane-layout/MaterialSupportingPaneLayout.vrt.test.tsx` — `COMPACT_VIEWPORT = { width: 375, height: 667 }`, `EXPANDED_VIEWPORT = { width: 1024, height: 768 }`).

  - Context-consumer tests without a provider (`layouts/navigation-rail-layout/MaterialNavigationRailLayoutMenuButton.test.tsx`).
  - `// Written by <model name>` header comment (agent-authored test files, prior batches).
  - Absence assertions: `not.toBeInTheDocument()`, hidden elements via `{ includeHidden: true }` + `not.toBeVisible()`.

- **Key source facts the tests must respect** (verified by reading the sources):
  - `MaterialCarousel` drag: `createPerPointerListeners` on the `sm-carousel` ref; `onDown` only registers move/up handling when `pointer.pointerType !== 'touch' && pointer.pointerId === pointerId()`; `pointerId` is set by `onPointerEnter` on `sm-carousel` (line 55) and cleared by `onPointerLeave` (line 56). Drag applies `scrollLeft = startPosition - dx` and toggles `bool:data-dragging`.
  - `MaterialRadio`: `md-radio` sets its role via element internals — `getByRole('radio')` cannot resolve it (documented in the radio VRT header); locate via `getByElement('md-radio')` and assert state through the `checked` attribute. The `onChange` handler guards `event.target !== null && isRadio(event.target)` (`'checked' in target`). `md-radio` is form-associated, so the host element itself exposes `checked` — a synthetic `change` dispatched on the host passes the guard; dispatch a non-radio `change` from a light-DOM child inside the host instead (see step 5).
  - `MaterialSideSheet` (rendered by `MaterialSupportingPane` at expanded width): its close icon button has **no accessible name** (SupportingPane does not pass `closeButtonAriaLabel`), and closing is asynchronous — the click runs `setOpen(false)`, the dialog `close()` happens after a 250 ms `setTimeout`, and only the dialog's `toggle` event (newState `'closed'`) invokes the user `onClose` — assertions need `vi.waitFor`.
  - `MaterialBottomSheet` modal (compact-width SupportingPane): a `<dialog closedby="any">`; the established way to close it in tests is `userEvent.keyboard('{Escape}')` (`MaterialBottomSheet.test.tsx`; direct dialog clicks are flaky — issue #3 noted there).
  - `MaterialSnackbarModal` renders `<div popover="manual">` — UA styling hides popover elements until `showPopover()`, which normally happens in `SnackbarTransition.onEnter`. A standalone render must call `showPopover()` on the modal's popover div from the test fixture (mirroring `onEnter`) or the buttons are not visible/clickable.
  - `MaterialTheme`: the **baseline** stylesheet defines `--md-ref-palette-*` tokens (`material-theme-baseline.tsx`), the **dynamic** one (only with a `theme` prop) defines `--md-sys-color-*` (`material-theme-dynamic.tsx`) — token assertions must use the right names per mode (corrects the original gap analysis, which quoted `--md-sys-color-primary` for the baseline render). Colors are observable via `getComputedStyle(document.documentElement).getPropertyValue(...)`.
  - `MaterialNavigationItem` renders `<A>` (router) with `role="menuitem"`, so rail tests need the router wrapper; secondary rail items are `disabled={!isVisuallyExpanded() || item().disabled}` — pass `expanded: true` to distinguish item-level disability from collapse-induced disability.
  - Icons import from `@solidmaterial/icons` and must sort last (`.oxfmtrc.json`); oxfmt formats, oxlint enforces `max-lines` 1000 and justified disable comments.

## Risks and open questions

- **Synthetic pointer events are novel here** (step 2 drag tests): no existing test dispatches `PointerEvent`s. The guard needs `pointerId` equality, so the plan is a fully synthetic sequence (synthetic `pointerenter` with `pointerId: 1` → `pointerdown` → `pointermove`(s) → `pointerup`, dispatched on `sm-carousel` with `bubbles: true` so both element- and window-level listeners from `@solid-primitives/pointer` receive them). If the per-pointer move/up listeners turn out to attach elsewhere, verify the listener target in the package source and adjust the dispatch target; the fallback is `userEvent.hover` (CDP mouse, `pointerId` 1) to set the id and synthetic downs/moves to drag.
- **Fake timers in browser mode are novel here** (step 9): install with `vi.useFakeTimers({ shouldAdvanceTime: true })` so real time keeps ticking for CDP queries/expect polling, use `await vi.advanceTimersByTimeAsync(...)`, and avoid `vi.waitFor`/`expect.poll` in those tests. If fake timers still misbehave with browser locators, the fallback for the 4 s case is a real-time wait; the 10 s cases then stay fake-timer-only or are reduced to asserting the timer was scheduled (spy-based) — decide during implementation.
- **Standalone `MaterialSnackbarModal` is hidden until `showPopover()`** — the fixture must call it (or wrap in the exported `SnackbarTransition`); do not "fix" visibility by changing production code.
- **`MaterialTheme` unmount uses `adoptedStyleSheets.splice(index)` without a delete count** (removes all trailing sheets) — in the single-render test this is equivalent to removing just the theme's sheet, but if the unmount test observes collateral removal (e.g. the typescale sheet) that is a production bug to report, not fix — out of this spec's scope.
- **`MaterialTheme` token-name correction**: the gap analysis quoted `--md-sys-color-primary` for the baseline stylesheet, but the baseline generator only emits `--md-ref-palette-*` tokens; `--md-sys-color-*` tokens come from the dynamic generator (and possibly static CSS). The step 13 assertions are written accordingly; if `material.css` already defines static sys tokens, the differ-between-baseline-and-dynamic assertions still work.
- **`useContext` inside `showSnack`** relies on Solid ≥ 1.9 preserving owner context in event handlers — established library behavior (peer dep is `^1.9.0`); if the context test finds `showSnack` returning early in a click handler, that's a production finding to report, not fix.
- **Coverage comparison scope**: the baseline table in Current state came from a full-package istanbul run; step 15 instead re-measures both sides itself with an identical command shape (components + visual, once without and once with the 13 new files), so the delta is apples-to-apples regardless of the original scope — expect the fresh "before" numbers to differ slightly from the table numbers, though the table's uncovered line/branch references are unaffected by which projects run. Treat "all listed regions covered" as the primary criterion rather than exact percentages.
- **Open**: the compact-height rail-layout case (step 12 optional test) is the only one whose viewport (1024×400) is below the common sizes — if the orchestrator scales or clips it oddly, drop the optional test and note the gap (the `props.fab` ternary arms remain partially covered).
- **Open**: md-menu-item/md-sub-menu standalone rendering (steps 3–4, outside an `md-menu`) is assumed to work since they're plain DOM listeners/bindings; if the web components error standalone, wrap the subjects in a minimal `<md-menu>` (e.g. via `MaterialMenu`) and keep the assertions unchanged.
