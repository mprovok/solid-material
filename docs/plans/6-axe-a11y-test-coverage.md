# Axe accessibility tests across the component library

## Summary

Add the first consumers of the repo's axe-core harness: a `describe('Accessibility')` block with at least one `axe()` scan — plus the structural role/ARIA assertions that document the wiring — in every component test file for the ~30 components the coverage review identified. 17 existing `*.test.tsx` files are extended; 15 new `*.test.tsx` files are created for components that have no interaction test at all (select, text-field, password-field, side-sheet, menu, tabs, fab, icon-button, navigation-item, chip, chip-set, progress, divider, typography, app-bar). Production code is not touched, no VRT files or baselines are involved, and no changeset is needed (`*.test.*` is excluded from the published build).

## Current state

- **The harness exists but has never been used.** `packages/material/vitest.axe.ts` exports `axe(element, overrides?)` and registers the `toHaveNoViolations` matcher. It is wired as a setup file **only in the `components` project** (`packages/material/vitest.config.ts`, line 87) — it does not exist in `*.vrt.test.tsx` or storybook tests. A grep for `await axe(` across `packages/material/src` returns nothing: every file in this spec is the harness's first consumer. Import shape from a component test: `import { axe } from '../../../vitest.axe'`.
- **Usage shape** (per the `write-tests` skill): `const { container } = render(...)` then `await expect(await axe(container)).toHaveNoViolations()`. Scope is `container` (never `baseElement`/body — document-level rules like `html-has-lang` fire identically in every test otherwise). The default config already disables `button-name`, `empty-heading` and `region`, mirroring `.storybook/preview.tsx`; never re-disable those per call. Per-call overrides for rules that fire for known-accepted reasons need a justifying comment.
- **axe-core pierces open shadow roots**, so the `md-*`/`sm-*` internals of the thin `@material/web` bindings are audited too. Violations originating inside `@material/web` internals are handled with justified per-call overrides, not by skipping the scan.
- **Overlays must be rendered open** — axe skips elements hidden by UA styling for closed dialogs/popovers. Dialog/side-sheet/bottom-sheet render nothing or an inert element unless `open`; `md-menu` items are only visible with `open: true` plus an anchor; plain tooltips open via anchor **focus** (450 ms debounce — needs `vi.waitFor` on the `tooltip` role) while rich tooltips with `persistent: 'mount'` render open immediately (`MaterialTooltip.tsx` line 28).
- **Established fixtures to reuse** (from the existing test files and spec `docs/plans/4-interaction-a11y-test-coverage.md`): `{ wrapper: MaterialTheme }`; router-dependent components (anything rendering `<A>` from `@solidjs/router`: navigation-item, navigation-rail items) need the `MaterialTheme` + `<Route path="*">` wrapper and the `location: '/'` render option; snackbar tests need a fresh `MaterialSnackbarContext.Provider` with a test-local `createStore` and `duration: 'indefinite'`; carousel fixtures reuse the network-free SVG graphic from `MaterialCarousel.vrt.test.tsx`.

## Acceptance criteria

- Every file listed in steps 1–28 contains a `describe('Accessibility')` block importing `axe` from `../../../vitest.axe` and using exactly `await expect(await axe(container)).toHaveNoViolations()` scoped to the render `container`; the globally pre-disabled rules (`button-name`, `empty-heading`, `region`) are never re-disabled, and any per-call override carries a justifying comment.
- Every scan is preceded by structural assertions (role query, accessible name, `toHaveAttribute`) for the state under test, so the file documents the wiring as well as sweeping it.
- Overlay components (dialog, bottom-sheet, side-sheet, menu, tooltip, fab-menu, split-button's menu) are scanned in their **open** state — the scan target is visible before `axe` runs; dialog's closed render is additionally asserted to produce no dialog element.
- Form-control scans cover the state matrices listed per step (checkbox indeterminate, slider single vs range, radio grouping, password-field toggle naming).
- All files pass twice in a row via `pnpm --filter @solidmaterial/material exec vitest run --project components --browser chromium` (verified: 44 files / 256 tests green twice); and once on the second Chromium instance per the `run-tests` skill; never in parallel.
- Only the test files listed in steps 1–28 are created or modified; `git status` shows no production code, stories, VRT or baseline changes; `pnpm lint` and `pnpm format:check` pass; no changeset is created; nothing is committed.

## Risks and open questions

- **The axe helper has no existing consumer** — its runtime behavior (matcher shape, typing via the `Matchers` module augmentation, axe-core version behavior in browser mode) is unverified in practice. Step 1 is the serialized pilot gate: if the harness itself is broken, fixing `packages/material/vitest.axe.ts` is in scope (it is test infrastructure, not shipped code), but any such fix must be called out in the handoff.
- **Violations originating inside `@material/web` internals** (known candidates: `md-select` combobox semantics, `md-slider` focus order, contrast on `md-*-progress` indeterminate animations under headless rendering). These are handled with justified per-call rule overrides at the specific scan, never by widening the global defaults — and if a violation reflects a real upstream bug, it is reported in the handoff rather than silenced.
- **Browser choice** — **Chromium**, confirmed by the requester (the default instance, CI baseline). The orchestrator passes the choice down.
- **Focus-opened plain tooltip timing**: the 450 ms open debounce requires `vi.waitFor` on the `tooltip` role before scanning; if focus-based opening proves flaky in headless Chromium, scan only the rich `persistent: 'mount'` variant and note the gap.
- **`md-select` listbox contents** are not visible while closed; the scan audits the closed combobox only (label, error text, aria-label). Driving the md internals to open the listbox is out of scope for a first test file.
- **Snackbar harness constraints**: module-level default store leaks between tests — every scan must use a fresh provider/store, and `duration: 'indefinite'` so auto-dismiss cannot race the scan.
- **Router-dependent components** (navigation-rail, navigation-item) need the `<Route path="*">` wrapper + `location: '/'` render option; forgetting it fails with a missing-router error rather than silently passing.
- **Open**: whether axe-core's version in the catalog flags `aria-checked` on `role="switch"` anchors vs buttons inconsistently — if the button toggle scan trips a rule for the native-button-with-switch-role pattern, resolve from the ARIA spec (allowed: a `switch` role requires `aria-checked`; on a native `<button>` it is valid) before disabling anything.
