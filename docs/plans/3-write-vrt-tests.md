# Visual regression tests for body, navigation, list-detail, and supporting-pane layouts

## Summary

Add visual regression tests (VRT, `*.vrt.test.tsx` files using `toMatchScreenshot()`) for the four layout components that currently have no screenshot coverage: `MaterialBodyLayout`, `MaterialNavigationLayout`, `MaterialListDetailLayout`, and `MaterialSupportingPaneLayout` (all under `packages/material/src/layouts/`). The layout implementations have already been reviewed with no major findings, so the baselines capture the current reviewed visual state as-is — no production code changes are expected or in scope; the finished test implementation itself must also pass a review with no major findings. All four files include interaction (drag-handle keyboard moves, rail expand/collapse via the menu button, supporting-pane open/close, snackbar-above-FAB). Unlike the previous two batches, layouts are breakpoint-driven, so the tests introduce viewport resizing through the Vitest 4 `page.viewport(width, height)` browser API (verified available in the installed `@vitest/browser@4.1.11`) to capture compact (375×667), medium (800×720), and expanded (1024×768 default) states. Tests are developed, run, and baselined against **Chromium** on Linux (`-chromium-linux.png` baselines, following the previous batches' precedent); WebKit (`-webkit-darwin`) baselines are explicitly out of scope and will be added later in CI — this gap is accepted and must not be "fixed" by committing Linux-generated WebKit baselines. Nothing is committed by the implementing agent — all new files are left in the working tree for the requester to commit.

## Risks and open questions

- **`page.viewport()` is novel in this repo** — the API is verified in the installed `@vitest/browser@4.1.11` types and implementation (it sizes the test iframe; it is provider-agnostic, so the same tests will also produce WebKit baselines in CI later), but no existing VRT file uses it. If it misbehaves (e.g. media queries not updating before render), insert a short `vi.waitFor` on `window.innerWidth`/`matchMedia` after the call; the fallback is to keep only the default-viewport (1024×768, expanded) states and note the compact/medium gap.
- **Viewport persistence and scale** — a viewport change leaks into subsequent tests in the same file (mitigated by the always-set helper) and sizes larger than the tester page viewport (1280×720) are CSS-downscaled; keep every requested size ≤ 1280×720. The expanded default 1024×768 is intentionally scaled 0.9375 exactly like every existing baseline, so comparisons stay deterministic; any WebKit rendering differences are a CI baseline concern, not a test change.
- **Drag-handle state determinism** — the activated (`data-active`) capture includes the focus ring and handle elevation; the click-then-`{Enter}` pattern is proven by the bottom-sheet VRT test. Pane-width transitions only run while the spacer is active, so keep the handle activated (or settle after deactivation) before the hidden-pane captures; the 800 ms settle covers the `--md-sys-motion-duration-standard-spatial-fast` transition. If the focus ring renders non-deterministically, capture the activated state without asserting the ring (the `data-active` attribute assertions remain).
- **Rail layout memo semantics** — `MaterialNavigationRailLayout`'s `isExpanded` is initialized from `Breakpoints.isExtraLargeWidth()` (false at all chosen sizes) and only toggled via the menu button; test first-render states and drive expansion only through the menu button (mirroring the story's play function), never by resizing after render.
- **Snackbar capture** — the snackbar is a popover anchored to the navigation bar, enqueued through a fresh context store; if the anchored position or enter transition proves flaky in Chromium, drop that single test rather than re-baselining blindly — it is the layout's only snackbar-specific capture. It is ordered last in the file as an extra guard against store leaks.
- **Bottom sheet in the compact modal supporting pane** — the sheet opens on mount (the visibility observer's has-been-visible guard prevents immediate self-closing) and scrolls into view with a scroll-driven animation; if the capture is mid-scroll, lengthen the settle for that file or adopt the bottom-sheet VRT test's two-rAF `onMount` opener. The sheet must fit inside 375×667 with the small 'Supporting content' child.
- **`getByRole` absence assertions** — Vitest browser locators have no `queryBy*`; absence is asserted with `expect.element(getByRole(…)).not.toBeInTheDocument()` (proven in `MaterialNavigationRailLayoutMenuButton.test.tsx`) — hidden-but-present panes (inert + `aria-hidden`, width 0) are excluded from role queries by default, which is exactly the story's `queryByRole(…)).toBeNull()` semantics.
- **File size** — the navigation-layout and list-detail files are the largest (fixtures + viewport matrices); keep fixtures shared at the top of each file and prefer `it.each` over copy-pasted tests to stay under the `max-lines` 1000 limit.
- **WebKit baselines** — until CI generates `-webkit-darwin` baselines on macOS, the visual project fails on WebKit for these four files; this is explicitly accepted for this task and must not be "fixed" by committing Linux-generated WebKit baselines.
