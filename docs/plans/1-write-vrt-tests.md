# Visual regression tests for focus ring, ripple, list, carousel, search, and navigation rail

## Summary

Add visual regression tests (VRT, `*.vrt.test.tsx` files using `toMatchScreenshot()`) for the six components that currently have no screenshot coverage: `MaterialFocusRing`, `MaterialRipple`, `MaterialList`/`MaterialListItem`, `MaterialCarousel`/`MaterialCarouselItem`, `MaterialSearchBar`, and `MaterialNavigationRail`. The component implementations have already been reviewed with no major findings, so the baselines capture the current reviewed visual state as-is — no production code changes are expected or in scope. Tests are developed, run, and baselined against **Chromium** on Linux (`-chromium-linux.png` baselines, following the existing `MaterialButtonGroup`/`MaterialSideSheet` precedent); WebKit (`-webkit-darwin`) baselines are explicitly out of scope and will be added later in CI. Interactive-state captures (hover, pressed, keyboard focus, open dialogs) appear only in the focus-ring, ripple, and carousel files; the list, search-bar, and navigation-rail files are static-only, with the search-bar file rendering the bar standalone — no `MaterialSearch` dialog wrapper, scrim, or fullscreen captures. Nothing is committed by the implementing agent — all new files are left in the working tree for the requester to commit.

## Risks and open questions

- **Focus-visible screenshots are novel** — no existing VRT file screenshots a keyboard-focused element. `userEvent.tab()` dispatches trusted key events, which should trigger `:focus-visible` in headless Chromium; if the ring does not render, fall back to the `visible: true` cases only and note the gap.
- **Ripple press capture** — the md-ripple fade-in may outlast the 800 ms settle; tune `SETTLE_TRANSITIONS_MS` if the pressed screenshot has not converged. The `pressAndHold` race is proven on buttons; attaching `md-ripple` to a plain `div` is what list/carousel items already do, so behavior should match.
- **Search bar standalone rendering** — low risk: the bar renders without the `MaterialSearch` wrapper (both contexts have defaults; `MaterialSearchBar.test.tsx` already renders it standalone), so the dialog-closed CSS dependency (`.wrapper .dialog { display: flex }`) no longer applies — no dialog is rendered at all. Remaining timing concerns are the leading/trailing button fade-in (`opacity` transition + `@starting-style`) and the focused-input caret, both handled by the settle wait / `caret-color` fallback in step 5. Accepted gap: the docked margins beside the bar and its `min-width`/`max-width` come from `.container` in `MaterialSearch.module.css` (search-view styling) and are not captured by this file.
- **Carousel** — content must be network-free (inline SVG), and a fresh render's `scrollLeft` is 0 (deterministic). The `full-screen` variant opens a modal dialog; screenshot the dialog element (side-sheet precedent). Keep the non-fullscreen screenshot target (wrapper including header/show-all button) consistent across tests.
- **Navigation rail memo semantics** — `isExpanded`/`isModal`/`isCenter`/`isHideWhenCollapsed` (`createMemo` with previous value) keep stale values when `show` is false; only test first-render states, and expanded states need the settle wait for the width/row-gap springs.
- **Flaky interactive states** — the only interactive captures are in the focus-ring, ripple, and carousel files (list, search bar, and navigation rail are static-only per requester decision); if a hover/press/focus screenshot proves non-deterministic across runs, drop that specific test — the static-state matrix is the deliverable.
- **WebKit baselines** — until CI generates `-webkit-darwin` baselines on macOS, the visual project fails on WebKit for these files; this is explicitly accepted for this task and must not be "fixed" by committing Linux-generated WebKit baselines.
